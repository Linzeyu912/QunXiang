# YingHe 跨仓库管理规范（分发副本）

本文件是当前一方仓库内的同版本分发副本。修改本规范时，必须在 `YingHe-entity`、`YingHe-story`、`YingHe-music`、`YingHe-storyboard-video`、`QunXiang` 与 `ShengYing` 同步同一 `policy_version`。`YingHe` 总仓恢复可访问后，应将此文件迁入总仓作为权威副本，并由各分仓链接该副本；在此之前，不以失效链接替代可审阅的本地规范。

## 1. 仓库边界与权威来源

| 类型 | 仓库 | 只存放的权威内容 | 不应存放的内容 |
| --- | --- | --- | --- |
| 统筹 | `YingHe` 总仓 | 项目定位、规范、里程碑、跨仓目录与稳定成果索引 | 分组源码、完整生产档案、运行数据、原始媒体 |
| 研发分仓 | `YingHe-entity`、`YingHe-story`、`YingHe-music`、`YingHe-storyboard-video` | 各组源码、数据契约、设计、调研、可复现实验及正式生产档案 | 其他组的同一资产副本、产品部署状态 |
| 产品集成 | `QunXiang`、`ShengYing` | 经验证的产品实现、发布配置、集成测试与面向用户的资料 | 分组的完整研究过程、原始媒体/模型缓存 |
| 外部依赖 | `third_party/*`（如 `VoxCPM`） | 上游源码与可验证的版本信息 | 项目补丁、项目文档、密钥和生成物 |
| 历史备份 | `backups/*` | 只读快照与恢复说明 | 日常开发、自动拉取或新功能 |

一个事实只能有一个权威仓库。跨仓交接只记录“来源仓库、相对路径、提交号或标签、资产/作品/镜头 ID、必要时 SHA-256”，不复制正文、媒体或工程目录。产品仓只通过经过验证的合并或升级接收研发成果，不能反向无记录地修改分仓权威资产。

## 2. 分支、提交与发布

- `main` 只接收可构建、可验证的合并；禁止强推、重写共享历史和绕过评审直接提交。
- 日常工作使用短生命周期分支：`feature/`、`fix/`、`docs/`、`chore/` 或现有 `codex/` 约定。跨仓变更在合并前列出涉及仓库和交接提交号。
- 提交信息使用既有中文前缀：`[新增]`、`[更新]`、`[修复]`、`[整理]`、`[同步]`、`[归档]`；一次提交只解决一个可说明的变更。
- 面向交付的版本以带注释的标签标记；产品仓的集成提交必须记录所消费分仓的仓库、提交号、接口/资产版本与验证结果。
- 数据契约、接口或资产 ID 改动必须同时更新规格、兼容策略和相关测试；破坏性改动先发出版本化迁移说明。

## 3. 文件与 Git LFS 分流

| 内容 | 存放方式 |
| --- | --- |
| 源码、配置、Markdown、可审阅的小型 JSON/CSV、测试夹具 | 普通 Git；单文件原则上不超过 5 MiB |
| 正式音频、视频、成片、设计源文件、Office 原件、压缩交付包、不可高效文本 diff 的二进制资产 | 需入库时默认使用 Git LFS；5–500 MiB 为强制区间，并保留 README/元数据、来源、用途、版本与校验值 |
| 超过 500 MiB 的媒体、原始数据集、模型权重、模型/包缓存、可重新生成的导出物 | 对象存储、模型仓或制品库；Git 只保存下载脚本、清单、许可证和 SHA-256。LFS 例外须经仓库负责人确认配额、授权与保留期限 |
| 密钥、Cookie、个人信息、未获授权的声纹/人像、运行数据库、上传目录、日志、临时输出 | 永不入 Git 或 LFS；放入受控运行环境并由 `.gitignore` 覆盖 |

Git LFS 用于需要随代码版本长期交付的二进制成果，不是缓存盘。预训练基础模型、Hugging Face/ModelScope 缓存、`node_modules`、虚拟环境、可由构建恢复的包和批量中间渲染一律不进 LFS。

各仓库的 `.gitattributes` 只对新加入或经明确迁移的文件生效。已作为普通 Git blob 提交的大文件不得由个人直接重写历史；先统计影响、备份分支和远端 LFS 配额，再由仓库负责人安排 `git lfs migrate`、强推窗口与全员重新克隆。

## 4. 各仓库的落地规则

- `YingHe-entity`：结构化实体、设定和可复现的种子数据是权威来源。超过 5 MiB 的原文或机器生成快照先判断是否应进入对象存储；确需作为冻结发布样本时走 LFS，并保留生成版本和来源。
- `YingHe-story`：保留文本、故事资产、规格与案例的可审阅版本；原始版权文本、大批量语料和模型输出缓存不入库。正式报告采用同名 Markdown + Office 原件，原件走 LFS。
- `YingHe-music`：正式音频、音频工程交付和报告原件走 LFS；个人声纹原件、未授权参考音频、模型和批量生成输出留在受控存储。按 `line_id/shot_id` 记录来源与授权。
- `YingHe-storyboard-video`：`productions/` 中的正式视频、音频、压缩包和大图走 LFS；预训练模型、渲染缓存和未入选候选片段走制品/对象存储。作品档案始终记录 `production_id`、`shot_id`、来源版本和成片校验值。
- `QunXiang`：只纳入已验证的实体/故事产品能力；上传文件、运行数据库、原文和导出物不入库。产品集成须能追溯到来源分仓的提交和验证记录。
- `ShengYing`：只纳入已验证的音视频产品能力；原始音频、模型权重、第三方源码和生成视频默认由受控存储或上游仓管理。若必须保留小型回归夹具，使用范围受限的 LFS 路径并记录授权。

## 5. 文档、审核与例行检查

- 正式 Markdown 使用仓库既有 frontmatter；正式调研报告保留同名 Markdown 检索版和 Office 原件。旧档案只读，不把新工作写回 `docs/archive/YingHe-main/`。
- 提交前检查 `git status`、测试/构建、跨仓引用提交号和新增文件体积。加入 LFS 文件后检查 `git lfs ls-files`；发布或迁移后运行 `git lfs fsck`。
- 每月由各仓负责人复核：大文件清单、LFS 配额、失效外链、敏感数据扫描、依赖许可证、未合并分支和备份可恢复性。
- 任何例外必须在 PR 或变更记录中写明文件路径、大小、归属、保留期限、授权、存储位置和批准人。
